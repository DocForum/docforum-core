# ADR 0014: Lab result file storage (object storage provider)

- **Status:** Accepted
- **Phase:** 5 — Facilities & fulfillment
- **Issue:** [#16](https://github.com/DocForum/docforum-core/issues/16) — lab result attachment

## Context

ARCHITECTURE.md §2 says lab result files go to "object storage (S3-compatible)"
and must never be stored in Postgres rows, but did not name a provider or say
how files are read back. Issue #16 needs a concrete choice: a lab order a
facility fulfils needs its result attached for "fulfilled" to mean anything.

Constraints:

- These are medical records. PRD §7 limits them to the patient, the treating
  doctor(s) and the fulfilling facility for that specific order, the same as
  consultation notes. A public URL, or a URL someone could guess, is not
  acceptable.
- §1.5: use a managed provider behind an internal interface; don't build
  storage ourselves.
- The backend runs on Render (ADR 0003), whose disk is ephemeral, so the local
  filesystem can't hold files.
- Tests run with no network access to a cloud provider.

## Decision

1. **Provider: Amazon S3**, one **private** bucket per environment. "Block
   all public access" is on, and the server sends no ACLs. Every object is
   written with S3-managed server-side encryption (`SSE-S3`, `AES256`). S3 is
   the reference implementation of the API §2 already chose, and AWS signs
   HIPAA BAAs covering S3 if that becomes a requirement. Notification email
   is also on AWS (ADR 0013).
2. **Client: the official `@aws-sdk/client-s3`.** It is wrapped by
   `backend/src/utils/object-storage.ts` (`ObjectStorage`:
   `putObject`/`getObject`/`deleteObject`), and no other file imports the
   SDK. Because the client speaks the S3 API, any S3-compatible store works
   as a configuration change with no code change: set
   `OBJECT_STORAGE_ENDPOINT` + `OBJECT_STORAGE_FORCE_PATH_STYLE=true` for
   MinIO locally, or R2/Spaces if the provider changes.
3. **Files are served only through the API, never by URL.** Each object key is
   opaque and generated by the server (`lab-results/<random UUID>`). It
   contains nothing about the patient, the order or the uploaded filename,
   it is stored in `LabResult.resultObjectKey`, and it is never returned to
   a client. `GET /orders/lab-orders/:labOrderId/result` checks access on
   every request, writes an `AccessLog` row, and streams the bytes with
   `Cache-Control: no-store`. **Presigned URLs were rejected:** a presigned
   URL is a bearer credential. It can be forwarded, it stays valid until
   expiry even if access is revoked in the meantime, and reads made through
   it never reach the access log.
4. **Upload is a raw request body.** The `Content-Type` must be
   `application/pdf`, `image/png` or `image/jpeg`, and the file's first bytes
   must match that type. Size is capped by `LAB_RESULT_MAX_BYTES` (default
   10 MiB). No multipart dependency is added.
5. **Configuration** (`config.objectStorage`): `OBJECT_STORAGE_DRIVER`
   (`s3` | `memory` | `none`), `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_REGION`,
   and the optional endpoint/path-style settings. Credentials come from the
   AWS SDK default chain (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` or an
   instance role) and are never put in config objects or committed. `memory`
   is for tests and is refused when `NODE_ENV=production`. With no bucket
   configured the driver is `none`: the server still starts (the Render
   preview has no bucket), and the result endpoints return
   `503 OBJECT_STORAGE_NOT_CONFIGURED`. They never pretend to have stored
   anything.

## Consequences

- Downloads pass through the API process. With a 10 MiB cap and one file per
  lab order, this is acceptable for v1. Revisit if result files get large
  (imaging) or download volume grows. At that point, short-TTL presigned URLs
  issued *after* the same access check are the fallback, with the
  revocation/logging trade-off above accepted explicitly.
- Objects are never deleted by the application. `LabResult` is append-only,
  like the order it belongs to (hard rule 1), and account deletion anonymises
  rather than erases (ADR 0010). The one exception: if the database insert
  fails after a successful upload, the just-uploaded object is deleted
  (best effort, and unreachable through the API either way).
- Bucket lifecycle, versioning and cross-region backup are operational
  settings for the deployment (issue #22). They are not in the code.
- `PatientExportChunk` (ARCHITECTURE.md §6.3.4) stays in Postgres for now.
  This ADR makes S3 available for it, but moving export bundles is a
  separate change.

## Alternatives considered

- **Cloudflare R2 / DigitalOcean Spaces:** S3-compatible and cheaper egress,
  and still reachable later as a config change through the same client.
  Rejected as the default because they have no HIPAA BAA path today.
- **Postgres `bytea`:** rejected by ARCHITECTURE.md §2 directly. It bloats
  backups and every replica, and it mixes file blobs into the clinical record
  tables.
- **Hand-written SigV4 over `fetch`:** fewer dependencies, but it means
  writing request-signing code ourselves, against §1.5.
